02 / PROBLEM

How do two sides trust a payment?

A buyer wants proof that an item will arrive; a seller wants confidence the funds will be released. A mutable stored balance creates another piece of state that can drift away from the transaction history.

DESIGN QUESTION

Can every change in money and escrow state be explained by an append-only record of what happened, who caused it, and why?

03 / SYSTEM

Escrow is a state machine; money movement is a ledger event.

In the repository implementation, a buyer creates an escrow, funds it, and the seller marks it shipped. Delivery releases funds. A dispute moves the transaction into review, where it can be resolved or refunded.

Both legs of a money movement, the escrow status update, and its audit record are grouped in the same transactional service operation.

Spring Data JPA/Hibernate persists the domain records. A centralized transition service rejects invalid escrow state changes; service-layer ownership checks guard buyer/seller actions.

05 / DECISIONS

Correctness is encoded in the shape of the system.

  • Paired ledger entries: each transfer writes a debit and credit linked to the escrow reference.
  • Atomic money flows: funding and delivery confirmation use transactional service methods so state and ledger changes commit or roll back together.
  • One transition boundary: the state machine validates legal edges instead of allowing controllers to set statuses ad hoc.
  • Object ownership: buyer and seller actions verify the actor owns the relevant side of the escrow.
  • Concurrency and retries: escrow initiation requires an idempotency key; optimistic versioning protects concurrent updates.
  • Auditability: transition records preserve the from/to state, actor, reason, and timestamp. A scheduled job handles expiry/auto-release rules.
WHY NO BALANCE COLUMN?

A mutable balance can disagree with its transaction history. A derived balance makes the ledger the single source of truth: debit and credit entries explain every movement, and the same arithmetic can be recomputed for audit.

ACCOUNT VIEW = Σ CREDITS − Σ DEBITS

07 / CHALLENGES

Money and status must not disagree.

The core challenge is keeping an escrow transition, its money movement, and its audit trail consistent under retries or concurrent requests. The design puts the money legs inside transactional service methods, validates state centrally, and uses optimistic locking to make a conflicting update fail rather than silently double-release.

Idempotency is an area to examine carefully: the repository README notes that the current unique key rejects duplicates; stored-response replay is still on the roadmap. That distinction matters for a retry-safe payment API.

08 / VALIDATION

State what is verified—and what is still planned.

The repository documents transactional behavior, state validation, ownership checks, a unique idempotency constraint, and optimistic locking. Its README lists a state-machine test matrix and a concurrent release-race test using Testcontainers PostgreSQL as planned work.

No comprehensive financial correctness test suite is claimed here. The simulator above is not a substitute for backend integration tests.
09 / TECHNOLOGY

Built across the API, data, and interface layers.

Backend: Java, Spring Boot, Spring Security, JWT, BCrypt, Spring Data JPA, Hibernate.

Data: PostgreSQL, double-entry ledger, derived balances, transactional persistence, audit records.

Frontend: React, Vite, JavaScript, CSS.

Engineering concerns: RBAC and object ownership, idempotency key, optimistic locking, scheduled expiry, centralized state validation.

12 / LESSONS

Make the safest path the easiest path to inspect.

A ledger can make money movement explainable, but it does not remove the need for careful transaction design, a correct state machine, and honest retry semantics. The next useful proof is a concurrency-focused integration suite—not a bigger dashboard.
