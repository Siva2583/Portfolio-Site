02 / PROBLEM

Animation can show motion without showing reasoning.

When an algorithm is animated as it executes, it can be difficult to pause at a specific operation, revisit an earlier state, compare implementations, or explain what changed. AlgoViz makes execution inspectable by separating work from presentation.

CORE STATEMENT

Every state in the sorting lab is recorded before it is rendered for playback.

03 / SYSTEM

Generate once. Inspect at the learner’s pace.

The project contains a sorting laboratory and a wider library of algorithm modules. The sorting lab supports frame inspection, timeline seeking, playback controls, speed changes, and comparison by recorded operation counts. Other modules retain algorithm-specific execution implementations rather than sharing one universal playback reducer.

Experiments can be kept locally and exported or imported as JSON. Sorting inputs are intentionally bounded to 2–24 integers so full snapshots remain manageable.

04 / ARCHITECTURE

05 / DECISIONS

Choose inspectability—and make the cost visible.

  • Full snapshots: straightforward rewind and state inspection, at higher memory cost.
  • Stable IDs: values retain identity when duplicates move, making a trace reproducible and inspectable.
  • Bounded input: sorting inputs are capped instead of suggesting unbounded trace scalability.
  • Explicit playback state: reducer transitions make cursor, pause, replay, and seek behavior testable.
  • Local experiments: save recent work in the browser and exchange portable JSON, without introducing a backend.
  • Honest comparison: compare recorded operation counts, not wall-clock speed or heap usage.

BOUNDARY

For a quadratic algorithm, copying the complete array into each frame can grow to cubic trace storage. Compact events, checkpoints, and workers are future options—not current capabilities.

07 / CHALLENGES

History is useful only when its limits are understood.

Full snapshots make seeking easy to explain but consume more memory as traces grow. Separate playback ownership also means the sorting engine cannot be described as a shared framework for every module. The implementation bounds inputs and documents that difference instead of implying a general-purpose debugger.

The project is an educational visualization system: it does not execute arbitrary user code, run AI tutoring, or claim to be a runtime benchmark.

08 / VALIDATION

Correctness checks compare algorithms with simple oracles.

The repository documents 14 test groups, including seeded sorting cases and playback/validation checks. Its sliding-window reference check compares results with a brute-force oracle across 64 arrays × 12 targets = 768 cases. The supplied portfolio brief also cites 150 algorithm-input cases.

These are test inputs and comparisons—not performance claims or a proof of correctness for every possible input.

09 / TECHNOLOGY

A browser-driven tool with a small dependency surface.

Interface: React 19, JavaScript/JSX, Tailwind CSS, and custom styles.

Build and routes: Vite, React Router, lazy-loaded modules.

State and persistence: React state, a reducer for sorting playback, localStorage, JSON import/export.

Validation: Node.js test runner, ESLint, and Vercel deployment.

12 / LESSONS

A timeline is data, not time travel.

Recorded snapshots make inspection and replay simple, but cost memory. Naming that trade-off—and setting a bounded input size—is better engineering than hiding the cost behind a smooth animation.
