02 / PROBLEM

Career suggestions need more than a single label.

EDU2JOB takes a student’s degree, major, CGPA, and skills and returns a ranked shortlist of job roles. That requires a clear handoff between the web application and a model service, plus preprocessing that keeps categorical, numeric, and multi-valued inputs aligned with the fitted model.

CORE STATEMENT

Java owns application flow and persistence; the Python service owns feature transformation and model inference.

03 / SYSTEM

A three-tier prediction path with an explicit service boundary.

The React app sends the prediction request to Spring Boot. Spring applies application/authentication logic, forwards the data to Flask, persists prediction inputs and raw output, and returns the ranked result to the client. The browser does not call the ML service directly.

The model pipeline encodes categorical degree and major, scales CGPA, expands skill tokens, runs the Random Forest classifier, calibrates probabilities, and returns up to five ranked roles.

05 / DECISIONS

Keep model preprocessing next to the fitted model.

  • Single application entrypoint: the browser calls Spring Boot, not Flask directly.
  • Preprocess with the model: categorical encoding, numeric scaling, and multi-label skill encoding are part of the Python pipeline.
  • Calibrate probability outputs: the repository uses an isotonic calibration layer before ranking predictions.
  • Persist prediction history: Spring stores the submitted inputs and raw model response for later inspection.
  • Keep the service boundary explicit: Python serves the scikit-learn artifact; Java manages web application flow.

BOUNDARY TO KEEP IN VIEW

The model response is a recommendation, not a guarantee of career fit. The interface should not present model confidence as certainty.

07 / CHALLENGES

Preprocessing and service assumptions must agree.

Feature encoders expect a particular set of categories and skill tokens. If the Java boundary and Python model disagree about field names, ranges, or vocabulary, a request can fail or be silently interpreted incorrectly. The split keeps each role clear, but makes service configuration and contract validation important.

The current repository README also notes follow-up work around Spring-to-Flask timeouts, an externalized ML-service URL, and a versioned database migration path.

08 / VALIDATION

Do not replace an evaluation plan with an accuracy badge.

The repository documents a fitted Random Forest with isotonic probability calibration and top-five ranked output. Its README lists a model evaluation harness—including stratified validation, top-k accuracy, and calibration metrics—as planned work.

No model accuracy percentage, performance improvement, or prediction score is claimed here. JWT handling is present in the project; the current README lists role-based access control as roadmap work rather than a shipped feature.
09 / TECHNOLOGY

Two runtimes, one prediction contract.

Client: React 18 and JavaScript.

Application API: Java 21, Spring Boot 3.2, Spring Data JPA, Hibernate, JWT, BCrypt.

ML service: Python 3.11, Flask, scikit-learn, Pandas, NumPy, joblib.

Persistence: PostgreSQL.

12 / LESSONS

Integration is a contract, not just an HTTP call.

Separating business logic from model inference makes each layer easier to evolve, but only if the request shape, preprocessing vocabulary, service URL, and failure behavior stay aligned. The most valuable next step is a measurable evaluation and a resilient, configured service boundary.
